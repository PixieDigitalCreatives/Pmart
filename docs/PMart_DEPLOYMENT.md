# PMart Deployment — Render (API) + Vercel (web app)

```
Browser ──► https://<your-app>.vercel.app          (Vercel: static React build)
   │            └─ /api/*  ──rewrite──►  https://pmart-backend.onrender.com/api/*   (Render: Express API)
   └─ live updates (Socket.IO) ───────►  https://pmart-backend.onrender.com          (direct, WebSocket)
                                              └──► MongoDB Atlas
```

**Why the `/api` rewrite.** The sign-in refresh cookie must be first-party. `*.vercel.app` and `*.onrender.com` are
different sites, and Safari (and Chrome when third-party cookies are blocked) drop cross-site cookies, which would sign
users out every hour. With the rewrite the browser only ever talks to the Vercel domain. Socket.IO goes direct because
Vercel can't forward WebSockets; it authenticates with the access token, not cookies, so that is fine.

Files in the repo: `render.yaml` (Render Blueprint), `vercel.json` (build, rewrites, headers), `.vercelignore`,
`backend/.env.example`, `.env.example`.

## 0. Before you start
1. **MongoDB Atlas → Network Access:** allow Render to connect. The free plan has no fixed IP, so add `0.0.0.0/0`
   (keep a strong database password). Paid Render plans list static outbound IPs you can allow instead.
2. **MapTiler:** create a **new** key (the current one is in git history), restrict it to your Vercel domain, and
   delete the old one after the switch.
3. Push the code to GitHub (`PixieDigitalCreatives/Pmart`). Both services deploy from the repo.
4. Have these ready (don't reuse the local development `JWT_SECRET`; it fails production rules):
   - `MONGODB_URI` — Atlas connection string.
   - `OTP_ENCRYPTION_KEY` — keep the one in `backend/.env` if you use the same database (codes already issued stay readable).
     New database: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

## 1. Backend on Render
1. Render dashboard → **New → Blueprint** → choose the repo. Render reads `render.yaml` and proposes the
   `pmart-backend` web service (root `backend/`, `npm ci`, `npm start`, health check `/api/health`, region Singapore).
   If you already created `pmart-backend` from the earlier blueprint, Render updates that service instead.
2. Fill in the values marked "sync: false":

   | Key | Value |
   |---|---|
   | `MONGODB_URI` | your Atlas URI |
   | `OTP_ENCRYPTION_KEY` | 64 hex characters (see above) |
   | `ALLOWED_ORIGINS` | **required** — your exact Vercel production URL(s), e.g. `https://pmart.vercel.app` (comma-separate several, `https://` only, no `*`). The API refuses to start in production without it. Use the project's `https://<project>.vercel.app` name if the domain is not known yet and correct it after step 2 |
   | `MAPTILER_API_KEY` | optional (server-side address lookup) |
   | `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` | optional, all three for Google sign-in |

   Set by the blueprint: `NODE_ENV=production`, `NODE_VERSION=20`, `PORT=5000`, `MONGODB_DB_NAME=pmart`,
   `JWT_SECRET` (generated by Render), `COOKIE_SAME_SITE=strict`, `TRUST_PROXY=2`, `OTP_LENGTH=4`, `LOG_LEVEL=info`.
3. Deploy, then open `https://pmart-backend.onrender.com/api/health` → `{"status":"ok","database":"connected",…}`.
   If Render gave the service a different URL (name taken), use that URL everywhere below.
4. **Database setup** (only for a new, empty database — the current Atlas database is already initialised and has an
   admin): run from your computer with `MONGODB_URI` pointing at the production database:
   ```bash
   cd backend && npm run db:init
   npm run create-admin -- --name "Your Name" --phone 98XXXXXXXX
   ```
   (On a paid plan you can run the same commands in the Render **Shell**.)

## 2. Web app on Vercel
1. The live API is `https://pmart-66mp.onrender.com`. If yours is different, edit both the `/api/:path*` destination
   and the `Content-Security-Policy` `connect-src` entries (`https://…` and `wss://…`) in `vercel.json` and commit them
   (Vercel config can't read environment variables). A wrong `connect-src` makes the browser block every socket call.
2. Vercel → **Add New → Project** → import the repo. Root directory: the repository root. Vercel reads `vercel.json`
   (Vite, `npm ci`, `npm run build`, output `dist`).
3. **Environment Variables** (Production, and Preview if you use previews):

   | Key | Value |
   |---|---|
   | `VITE_SOCKET_URL` | `https://pmart-backend.onrender.com` |
   | `VITE_MAPTILER_API_KEY` | the new MapTiler key |
   | `VITE_FIREBASE_*` | optional, only with Google sign-in (also add the Vercel domain to Firebase → Authentication → Authorized domains) |
   | `VITE_API_BASE_URL` | **leave unset** |

   `VITE_*` values are baked in at build time — redeploy after changing them.
4. Deploy. Put the production URL (e.g. `https://pmart.vercel.app`, no trailing slash) into Render's `ALLOWED_ORIGINS`
   and let Render redeploy. Add a custom domain later the same way (Vercel domain + `ALLOWED_ORIGINS`).

## 3. Check it
1. `https://<your-app>.vercel.app/api/health` returns the health JSON (the rewrite works).
2. Sign in at `/login` with the admin account; reload the page after a few minutes — you stay signed in (cookie works).
3. In the browser dev tools → Network → WS, the `socket.io` connection to Render shows status 101.
4. Type a wrong password once, then check Render → Logs: `Failed login from <your public IP>`. If it shows a Vercel
   address instead, client IPs are wrong (all users would share one rate limit) — tell the maintainer; `TRUST_PROXY`
   may need adjusting.
5. Place a test order end to end only on a test database, or delete what you create afterwards.

## Things to know
- **Render free plan** sleeps after 15 minutes without traffic. The next request waits for a cold start (often
  30–60 s) and live updates disconnect while asleep. Use the Starter plan for real customers.
- **Preview deployments** get random `*.vercel.app` URLs that are not in `ALLOWED_ORIGINS`, so their API calls are
  refused. Test on the production URL, or add a stable preview domain (e.g. the branch alias
  `https://<project>-git-<branch>-<team>.vercel.app`) to `ALLOWED_ORIGINS`. Wildcards such as `https://*.vercel.app`
  are refused in production: anyone can host a page on `vercel.app`, and the API answers credentialed requests.
- **Upgrading to the 2026-11-05 security release:** before Render deploys it, make sure `ALLOWED_ORIGINS` on Render
  lists every web origin exactly (the release stops accepting all `*.vercel.app` / `*.netlify.app` origins), and that
  `COOKIE_SAME_SITE` is `strict` or unset. If the new build fails to start, Render's log names the variable to fix.
- **Security headers** (CSP, HSTS, Permissions-Policy) are set in `vercel.json`. After a deploy, open the site with
  dev tools → Console and check there are no "Content Security Policy" errors on the home page, sign-in, admin live
  map and the address map.
- **Secrets** live only in the Render and Vercel dashboards. `VITE_*` values are public by design.
- **Netlify:** `netlify.toml` is from an earlier plan. If you stay on Vercel you can delete it; if you ever use Netlify,
  add an equivalent `/api/*` proxy redirect there instead of calling Render directly.
