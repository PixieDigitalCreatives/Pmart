# PMart Deployment — Render (API) + Vercel (web app)

_Updated 2026-11-05 for the custom domains `thepmart.in` (web) and `api.thepmart.in` (API)._

```
Browser ──► https://www.thepmart.in  (and thepmart.in)      Vercel: static React build
   ├─ REST  ──────────────────────►  https://api.thepmart.in/api/*   Render: Express API
   └─ Socket.IO (WebSocket) ──────►  https://api.thepmart.in         Render
                                         └──► MongoDB Atlas
```

**Why the browser calls `api.thepmart.in` directly.** The sign-in refresh cookie must be first-party.
`www.thepmart.in` and `api.thepmart.in` share the registrable domain `thepmart.in`, so they are the **same site**: the
cookie is sent with `SameSite=Strict` even though the API is on another origin (CORS allows exactly
`https://thepmart.in` and `https://www.thepmart.in`). Calling the API directly also means Render sees each user's real
IP with `TRUST_PROXY=1`, so a client can't fake its address to dodge rate limits (audit finding F2). The old
`/api/*` rewrite in `vercel.json` still points at `api.thepmart.in`; the app itself doesn't need it (only the
keep-alive ping and browser tabs opened before the switch use it).

Files in the repo: `render.yaml` (Render Blueprint), `vercel.json` (build, rewrites, headers), `.vercelignore`,
`backend/.env.example`, `.env.example`.

## 0. Before you start
1. **MongoDB Atlas → Network Access:** allow Render to connect. The free plan has no fixed IP, so add `0.0.0.0/0`
   (keep a strong database password). Paid Render plans list static outbound IPs you can allow instead.
2. **MapTiler:** create a **new** key (the current one is in git history), restrict it to your Vercel domain, and
   delete the old one after the switch.
3. Push the code to GitHub (`PixieDigitalCreatives/Pmart`). Both services deploy from the repo.
4. Have these ready (don't reuse the local development `JWT_SECRET`; it fails production rules):
   - `MONGODB_URI` — Atlas connection string.
   - `OTP_ENCRYPTION_KEY` — keep the one in `backend/.env` if you use the same database (codes already issued stay readable).
     New database: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

## 1. Backend on Render
1. Render dashboard → **New → Blueprint** → choose the repo. Render reads `render.yaml` and proposes the
   `pmart-backend` web service (root `backend/`, `npm ci`, `npm start`, health check `/api/health`, region Singapore).
   If you already created `pmart-backend` from the earlier blueprint, Render updates that service instead. (The live
   service `pmart-66mp` resolves to a US-West origin, not Singapore; the region can't be changed after creation, so a
   Singapore service would have to be created anew if latency from India matters.)
2. Fill in the values marked "sync: false":

   | Key | Value |
   |---|---|
   | `MONGODB_URI` | your Atlas URI |
   | `OTP_ENCRYPTION_KEY` | 64 hex characters (see above) |
   | `ALLOWED_ORIGINS` | **required** — exact web production URL(s): `https://thepmart.in,https://www.thepmart.in` (`https://` only, no `*`). The API refuses to start in production without it |
   | `MAPTILER_API_KEY` | optional (server-side address lookup) |
   | `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` | optional, all three for Google sign-in |

   Set by the blueprint: `NODE_ENV=production`, `NODE_VERSION=20`, `PORT=5000`, `MONGODB_DB_NAME=pmart`,
   `JWT_SECRET` (generated by Render), `COOKIE_SAME_SITE=strict`, `TRUST_PROXY=1`, `OTP_LENGTH=4`, `LOG_LEVEL=info`.
   **An existing service keeps its dashboard values** — check `TRUST_PROXY` is `1` there (it was `2` while the web app
   went through the Vercel rewrite).
3. **Custom domain:** Render → service → Settings → Custom Domains → add `api.thepmart.in`. At the DNS provider add
   `CNAME api → pmart-66mp.onrender.com` (the service's own `*.onrender.com` name). Render issues the certificate.
4. Deploy, then open `https://api.thepmart.in/api/health` → `{"status":"ok","database":"connected",…}`.
5. **Database setup** (only for a new, empty database — the current Atlas database is already initialised and has an
   admin): run from your computer with `MONGODB_URI` pointing at the production database:
   ```bash
   cd backend && npm run db:init
   npm run create-admin -- --name "Your Name" --phone 98XXXXXXXX
   ```
   (On a paid plan you can run the same commands in the Render **Shell**.)

## 2. Web app on Vercel
1. `vercel.json` already points the CSP `connect-src` at `https://api.thepmart.in` / `wss://api.thepmart.in` (plus the
   old `pmart-66mp.onrender.com`). If the API ever moves, edit `connect-src` and the `/api/:path*` rewrite and commit
   them (Vercel config can't read environment variables). A wrong `connect-src` makes the browser block every API call.
2. Vercel → **Add New → Project** → import the repo. Root directory: the repository root. Vercel reads `vercel.json`
   (Vite, `npm ci`, `npm run build`, output `dist`).
3. **Environment Variables** (Production, and Preview if you use previews):

   | Key | Value |
   |---|---|
   | `VITE_API_BASE_URL` | `https://api.thepmart.in/api` |
   | `VITE_SOCKET_URL` | `https://api.thepmart.in` |
   | `VITE_MAPTILER_API_KEY` | the new MapTiler key (allow `thepmart.in` and `www.thepmart.in` in its MapTiler restrictions, or maps fail) |
   | `VITE_FIREBASE_*` | optional, only with Google sign-in (also add both domains to Firebase → Authentication → Authorized domains) |

   `VITE_*` values are baked in at build time — redeploy after changing them.
4. **Domains:** Vercel → Project → Settings → Domains → add `www.thepmart.in` and `thepmart.in` (one redirects to the
   other). At the DNS provider:
   - `www` → `CNAME` to the target Vercel shows for the project (e.g. `cname.vercel-dns.com` or a project-specific
     `*.vercel-dns-0xx.com` name).
   - `@` (the bare `thepmart.in`) → **only** the `A` record Vercel shows (e.g. `216.198.79.1`). **Delete every other
     `A`/`AAAA` record for `@`**, such as the registrar's parking or hosting address. With two `A` records, part of
     the traffic reaches the wrong server and Vercel can't issue the certificate.
   Vercel shows "Valid Configuration" and issues the certificates once DNS is right (minutes to a few hours).
5. Render's `ALLOWED_ORIGINS` must be exactly `https://thepmart.in,https://www.thepmart.in`.

## 3. Check it
1. `https://api.thepmart.in/api/health` and `https://www.thepmart.in/api/health` both return the health JSON.
2. `https://thepmart.in` and `https://www.thepmart.in` both open without a certificate warning.
3. Sign in at `/login` with the admin account; reload the page after a few minutes — you stay signed in (cookie works).
4. In the browser dev tools → Network → WS, the `socket.io` connection to `api.thepmart.in` shows status 101.
5. Type a wrong password once, then check Render → Logs: `Failed login from <your public IP>`. If it shows another
   address (a proxy), client IPs are wrong — `TRUST_PROXY` needs adjusting.
6. Dev tools → Console on the home page, sign-in, admin live map and the address map: no "Content Security Policy" errors.
7. Place a test order end to end only on a test database, or delete what you create afterwards.

## Things to know
- **Render free plan** sleeps after 15 minutes without traffic. The next request waits for a cold start (often
  30–60 s) and live updates disconnect while asleep. Use the Starter plan for real customers. The keep-alive
  (`.github/workflows/keep-alive.yml`, every 14 min from 07:30 to 00:30 IST, plus a ping from open browser tabs every
  10 min) works around it. On a private repository each run is billed as at least one GitHub Actions minute: 85 runs a
  day, about 2,550 a
  month — more than the free plan's 2,000, so GitHub may stop or bill the workflow.
- **Preview deployments** get random `*.vercel.app` URLs that are not in `ALLOWED_ORIGINS`, so their API calls are
  refused. Test on the production URL, or add a stable preview domain (e.g. the branch alias
  `https://<project>-git-<branch>-<team>.vercel.app`) to `ALLOWED_ORIGINS`. Wildcards such as `https://*.vercel.app`
  are refused in production: anyone can host a page on `vercel.app`, and the API answers credentialed requests.
- **Upgrading to the 2026-11-05 security release:** before Render deploys it, make sure `ALLOWED_ORIGINS` on Render
  lists every web origin exactly (the release stops accepting all `*.vercel.app` / `*.netlify.app` origins), and that
  `COOKIE_SAME_SITE` is `strict` or unset. If the new build fails to start, Render's log names the variable to fix.
- **Security headers** (CSP, HSTS, Permissions-Policy) are set in `vercel.json`. After a deploy, open the site with
  dev tools → Console and check there are no "Content Security Policy" errors on the home page, sign-in, admin live
  map and the address map.
- **Secrets** live only in the Render and Vercel dashboards. `VITE_*` values are public by design.
- **Netlify:** `netlify.toml` is from an earlier plan. If you stay on Vercel you can delete it; if you ever use Netlify,
  add an equivalent `/api/*` proxy redirect there instead of calling Render directly.
